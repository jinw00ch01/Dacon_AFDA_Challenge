Pro는 검수 작업본·QA 보고서·실험 review를 작성한다. Ultra는 release·실험 채택·학습 결과를 작성한다. GPU 학습, 임의 원격 명령, 상대 프로젝트 직접 수정은 맡지 않는다. CPU 작업은 harness의 역할 한도 내에서 실행한다.

코드 수정이 필요하면 목적별 브랜치 또는 별도 worktree에서 최소 변경과 검증 근거를 만들고 PR로 제안한다. 자동 동기화하는 main을 작업 중간에 갱신하거나 Ultra의 학습 config를 몰래 수정하지 않는다. 독립 작업본에 데이터가 필요하면 명시적으로 기존 읽기 전용 데이터 루트를 지정한다. venv나 원본을 통째로 복사하지 않는다.

## 학습 이전에 할 일

1. P0~P1: 원본 목록·출처·해시·전체 디코드 근거를 확인하고 중복 사건/주행을 묶는다. 첫 프레임 미리보기 생성 성공은 전체 디코드 또는 라벨 품질 검증이 아니다.
2. P2: 같은 사건, 원본과 재촬영, 같은 주행에서 잘라낸 모든 파생물이 같은 split인지 확인한다. 신규 Nexar의 사건 그룹은 검수 후 확정한다.
3. P3-S2: 기존 CSV에서 실제 접촉·차선 진입 적합성을 사람이 선별하도록 돕고 프레임 탐색, 누락·경계·타입 검사, blind 재검수 목록을 준비한다. 사람이 판단하지 않은 사고를 에이전트의 추측으로 `reviewed` 처리하지 않는다.
4. P3-S1: S23 파일 수신 후 이름·재생 원본·촬영 조건·SHA·디코드·품질을 검수한다. 원본/재촬영의 검은 테두리·해상도·오디오가 정답을 그대로 드러내는지 점검한다.
5. P3-S3: 센서 겹침·누락·단위·시간 원점·프레임 대응을 확인하고 제외 사유와 클래스 가설을 작성한다. SRC014를 보간해서 정답으로 복귀시키지 않는다.
6. 게이트별 `pass / blocked / excluded`와 근거 파일, 담당자, 시각을 Ultra에 전달한다. 라벨이 비어 있으면 다음 사람 작업을 구체적으로 표시한다.

현재 자동 반환 대상은 Nexar 검수 CSV, S23 촬영표와 `data/captures/s23/`의 MP4/MOV다. **새 QA·experiment 파일은 현재 worker가 자동 감시하지 않는다.** 새 규약 어댑터 구현 전에는 해당 산출물 전달을 별도 확인하고, 자동으로 보냈다고 보고하지 않는다. 두 CSV는 한 번에 한 작성자만 편집한다.

## Ultra 실험 결과를 받은 후

1. 패킷 완료 표시·목록·SHA를 확인한다. 유효한 새 결과에만 검토를 시작한다. 같은 결과 해시를 두 번 처리하지 않는다.
2. 예측 sample ID를 해당 release의 검증 정답과 조인한다. 중복·누락·split 혼입·프레임 범위를 검사한다. 모델을 다시 학습하지 않고 CPU로 지표를 독립 재계산한다.
3. Ultra 지표와 다르면 공식/진단 지표 혼동, 분모, 마스크, 시간 변환, 반올림부터 점검한다. 값이 일치하지 않으면 성능 개선 판정을 보류한다.
4. Stage별 전체 지표와 클래스·조명·날씨·사건 그룹별 실패를 분석한다. 분모가 작은 구간은 수와 사례를 함께 보고한다. 검증/테스트 라벨을 전처리 학습에 넣지 않는다.
5. 가장 큰 문제에 대해 **한 가지 변경**을 제안한다. 예: 시간 오차가 크면 먼저 프레임 매핑 검증, 특정 클래스 부족이면 데이터 보강. 여러 하이퍼파라미터와 전처리를 동시에 바꾸지 않는다.
6. review에는 관측 사실, 가설, 제안 변경, 예상 효과, 반증 조건, 예상 자원과 근거 파일을 분리한다. Ultra가 채택/거절/보류를 결정한다. 리뷰 전달은 곧 실행 승인이 아니다.

| 관측한 문제 | 먼저 확인할 것 | 확인 후 가능한 한 가지 제안 |
|---|---|---|
| 충돌 시점 오차가 일정 방향으로 밀림 | 원본 PTS·crop offset·라벨 정의 | 시간 매핑 수정; 수정 전 LR 튜닝을 하지 않음 |
| train만 개선되고 validation 악화 | 사건 그룹 누수·과적합·표본 수 | 데이터 문제가 없으면 학습 epoch 축소 등 하나만 비교 |
| S3 특정 클래스 예측이 거의 없음 | train의 클래스 수·센서 proxy 규칙 | train sampler 변경 또는 부족 클래스 데이터 확보 |
| S1 특정 화면에서만 높은 정확도 | 베젤·코덱·split별 촬영 조건 | 양 클래스의 crop/인코딩 처리 일치 |

위 항목은 관측 점수가 아닌 진단 순서 예시다. validation 결과에 맞춰 정답 정의를 바꾸지 않는다.

## 지표별 주의

- S1: Macro F1, 클래스별 recall 및 원본 group 수. 같은 원본의 두 촬영을 독립적인 일반화 증거 두 건으로 계산하지 않는다.
- S2: collision/entry의 유효 정답 수와 시간 오차, evasion/side의 분모와 분류 지표. 공식 상세 채점식을 확인하기 전 진단 MAE를 공식 점수라고 부르지 않는다.
- S3: 가감속 분류와 조향 분류를 구분한다. 조향 평가 제외 마스크는 정답 STOPPED 기준이며 예측 STOPPED 기준이 아니다. 모든 sample_index에는 조향 출력을 채운다.

## 재시작과 회차 종료

마지막 review와 수신 결과 해시부터 확인한다. 파일이 일부만 도착하면 대기한다. 변경 없는 상태에서는 새로운 제안을 억지로 만들지 않는다. 테스트 실패·해시 불일치·사람 라벨 필요 상태는 명시적으로 반환한다.

종료 보고에는 `입력 ID·SHA / 실행한 CPU 명령 / 검증 가능한 사실 / QA 또는 review 경로 / 미완료·사람 작업 / Ultra에 제안하는 다음 한 단계`를 기록한다.
